# E1-B 时间协议与下一批请求预算

## 共同时间协议 v1

物理 owner 用同一规则执行 B0/B1：每完成一个物理步，下一步不得早于上一步完成墙钟 + 原 dt（0.004 s）。不追赶落后帧，不改动作采样/速度，不为某组特设 sleep。同步推理等待使用原 drive targets 保持；异步推理期间只继续原已批准动作。没有候选时，两组均保持而不是继续释放。普通保持不调用旧 `hold()`，因为它会重新设置夹爪目标；直接保持驱动目标并调用原 tick/monitor。

这是一致的 minimum-dt 墙钟节奏，不是硬实时保障。每步物理计算、日志、视频、渲染/规划停顿使有效物理频率低于 250 Hz；记录全部墙钟与 step 间隔 min/mean/max，不隐瞒这些停顿。单 owner 渲染时没有第二物理线程，物理不能同时推进；两组 capture 时点/数量和视频设置相同。禁止只在 B1 放慢运动来掩藏延迟。

分别报告：

- 进程入口到关闭的墙钟（Python 主脚本采样点，不伪称含 OS 启动前时间）；CLI 版本/help preflight 各延迟。
- 初始化墙钟和物理步/时间，含原工程辅助 grasp，单独记录起点；每次新进程，不是状态克隆。
- cold_start_s：从放置阶段开始到首候选提交，包含首三图、序列化、子进程启动、stub等待/保持。各 worker 另有 start/end 单调时钟，可拆分进程启动等待；此字段不是纯服务端首 token 延迟。
- 放置阶段墙钟、物理时间、holding 步数、每原语起止、任务更新、快照、请求起止、候选采用/失效、STOP、独立评分。
- 真正重叠 = worker start/end 与 PRIMITIVE_START/END 区间的交集；不把空闲保持或评分算作动作重叠。stub 延迟重叠不能称真实模型加速。

放置阶段总墙钟预算 120 s，含 cold start、渲染、推理、执行、保持和评分。每请求 deadline = min(启动时间 + 30 s, 回合绝对截止时间)，准备输入耗时不能延长总截止时间。超时取消 worker，不重试；晚到结果即使完整也拒绝。on-time 候选可待提交至回合截止，但仍须满足全部绑定和新实际状态检查。原底层规划/primitive 有自身超时；hook 在步边界检查回合截止，worker 取消/关闭允许清理延迟，日志保留实际时间，不声称操作系统硬截止。

离线正常 stub 延迟 0.8 s；故障验证另行显式标注。无有效下一计划时演示保持 0.5 s 后终止本离线回合，不把“保持完”算作放置成功。
